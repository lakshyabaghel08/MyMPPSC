# Implementation report

App: **MyMPPSC** — a local-first MPPSC Prelims preparation app.
Version: 1.0.0 · Bank schema: 1.0.0 · Backup format: `mymppsc-backup` 1.0.0
Build: plain HTML/CSS/ES modules, no bundler, no framework, no runtime dependency.

This report states what was built, what was actually run against it, and what is
still missing or unverified. Everything marked *verified* below was executed in
this repository; nothing is claimed on the basis of inspection alone.

Notable things the tests prove rather than assume:

* the real `index.html` boots in jsdom, every route renders without an error notice, and the Import screen adds the demonstration bank through its own buttons;
* a full paper simulation can be started, answered, flagged, palette-navigated, autosaved, submitted and reported **through the DOM**, and the stored result matches the paper's question count;
* a paper with unknown rules cannot be scored until rules are configured;
* a wrong answer creates a mistake entry, escalates on repeat, auto-resolves on a later correct answer and can be reopened;
* revision interval changes are explained and stored as a numeric basis; guessed-correct shortens the next interval;
* analytics never count repeats as new coverage and label samples under three as insufficient evidence;
* import skips identical records, preserves user corrections when updating, creates placeholder papers without inventing metadata, and can be undone;
* backup round-trip validates and its SHA-256 matches;
* `tools/build-bank.mjs` output imports cleanly and keeps a missing answer key missing.

## 3. Known gaps and limitations

The full list is in [`docs/LIMITATIONS.md`](LIMITATIONS.md). The headline items:

1. **UI verification depth.** The UI is covered by a jsdom journey suite (8 tests) plus a manual checklist. There is no Playwright/Puppeteer browser suite, so real layout, responsive breakpoints, print output, service-worker behaviour and screen-reader output are not automatically verified.
2. **No real content and no syllabus** ship with the app; both come from your imports. Real-key accuracy is the user's responsibility.
3. **Per-browser storage.** No sync or automatic off-device backup; clearing site data removes progress unless a JSON backup was taken.
4. **Analytics evidence thresholds.** Under 3 scored answers a figure is labelled insufficient; under 5 no strong/weak verdict is given. This is deliberate, but it means a small bank produces few conclusions.
5. **Scale untested.** Tens of thousands of questions have not been benchmarked.
6. **No CSV export** for attempts or analytics; JSON only.
7. **Duplicates and near-duplicates are reported, not merged** — deliberate, but it means the user must resolve them.
8. **Mastery is never claimed.** "Mastered" is a scheduling state reached by repeated successful recalls; it is not evidence of retained knowledge.

## 4. Design decisions worth recording

* **Two-phase import.** Analysis is pure (no writes), so the summary the user sees is exactly what a confirm will write.
* **Corrections are append-only.** `user_corrections[]` entries carry `before` values; imported data stays reachable under `classification.original` and `supplied`. A re-import cannot destroy the user's work.
* **Scoring is pure and explicit.** Rules are resolved once at test creation, stored on the test, displayed in the report and never recomputed from current settings, so an old report cannot silently change.
* **Scheduling stores its reasoning.** Each revision record keeps `basis` (outcome, confidence, previous/new level, base days, ease, multiplier, time taken) plus a plain-language `reason`.
* **One id, many variants.** Bilingual questions share an id so no statistic can double-count them.
* **Labelling over guessing.** Missing keys, unknown rules, incomplete papers, unreviewed explanations and synthetic content are all surfaced as badges and warnings rather than filled in.
